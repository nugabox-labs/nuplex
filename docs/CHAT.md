# 채팅

프로필끼리 주고받는 **1:1 실시간 채팅**. 웹은 SSE 로, 앱은 FCM 푸시로 새 메시지를 받는다.

> **앱(nuplex-app) 담당자에게** — 웹 쪽 계약은 이 문서가 원본이다.
> 앱이 해야 할 일은 [§5](#5-앱이-해야-할-일)에 모여 있다. 계약이 바뀌면 여기에 쌓는다.

## 1. 무엇인가

- 대화 단위는 **프로필**이다. 계정이 아니라 "지금 이 브라우저 · 이 기기가 고른 프로필".
- 상대는 **관리자가 켜둔 프로필**(`profile.enabled = true`) 중 나를 뺀 전부.
- Plex 서버 주인(`plex_account.is_admin`)에게는 화면에서 **관리자 뱃지**를 단다. NUGA 가 여기 해당한다.
- 지금은 1:1 만 있다. 그룹 채팅은 화면에 "준비 중" 으로 안내만 하고 만들지 않았다.
- 목록 아래에 **「관리자에게 작품 신청하기」** 가 있다. 상대를 고르는 단계를 건너뛰고
  관리자(`is_admin`)와의 방으로 바로 들어가며, 입력창에 신청 서식이 채워져 있다.
  가장 잦은 용건이고, 형식 없이 오면 관리자가 되물어야 하기 때문이다. 서식은
  `components/chat-panel.tsx` 의 `REQUEST_TEMPLATE` 한 곳에만 있다.
  관리자가 없거나 내가 그 관리자면 버튼을 감춘다.

권한을 새로 두지 않았다. 관문은 여전히 공통 비밀번호 하나이고, 프로필은 신원 표시다
(AGENTS.md §2). 대신 **남의 대화는 id 를 알아도 못 연다** — 모든 조회가 참가자인지를 먼저 본다.

## 3. 실시간 (웹)

```
POST /api/chat/messages  →  INSERT  →  pg_notify('nuplex_chat', {...})
                                            ↓
                          GET /api/chat/stream (SSE)  →  브라우저
```

- 전송은 평범한 POST 다. 실시간이 필요한 건 **서버 → 브라우저 한 방향**뿐이라 웹소켓을 쓰지 않았다.
  SSE 는 역방향 프록시를 그냥 통과하고, 끊기면 브라우저가 알아서 다시 붙는다.
- NOTIFY 페이로드에는 **식별자만** 싣는다(`conversationId` · `messageId` · `participants` · `senderId`).
  NOTIFY 는 8000바이트 제한이 있어서 본문을 그대로 넣으면 긴 메시지에서 발송이 통째로 실패한다.
  받은 쪽이 신호를 보고 다시 읽어 간다.
- SSE 연결 하나가 **pg 커넥션 하나**를 잡는다. `LISTEN` 은 커넥션에 붙는 상태라 풀에서 빌려 쓸 수
  없기 때문이다. 그래서 브라우저당 연결도 하나만 연다(`components/chat-panel.tsx`).
  접속자가 크게 늘면 여기가 먼저 아프다 — 그때는 커넥션 하나를 여러 구독자가 나눠 쓰는 구조로 바꾼다.
- 프록시가 조용한 연결을 끊지 않게 25초마다 주석 한 줄(`: ping`)을 흘리고,
  `X-Accel-Buffering: no` 로 nginx 버퍼링을 끈다.

## 4. 푸시 페이로드

기존 알림 푸시와 **같은 형식 · 같은 규칙**이다([APP-INTEGRATION.md §3](APP-INTEGRATION.md#3-푸시)).
`type` 과 `route` 만 다르다.

```jsonc
{
  "notification": { "title": "보낸 사람 이름", "body": "메시지 앞 200자" },
  "data": {
    "v": "1",
    "type": "chat",
    "route": "/?chat=12",          // 12 = conversation.id
    "collapseKey": "chat-12"
  },
  "android": { "notification": { "channel_id": "chat" } }
}
```

- `title` 은 **보낸 사람의 프로필 표시 이름**이다.
- `route` 는 완전한 URL 이 아니라 **경로**다. 셸이 `webBaseUrl + route` 로 조립한다.
- `collapseKey` 가 대화 단위라, 안 읽은 사이에 여러 통이 와도 알림줄에는 마지막 하나만 남는다.
- Android 채널을 `chat` 으로 지정해 보낸다. 지정하지 않으면 앱이 백그라운드일 때
  시스템이 기본 채널(`general`)로 그려서, 사용자가 채팅 알림만 꺼도 백그라운드에서는
  계속 온다. 채널 목록은 앱이 만든다(`nuplex-app/docs/PUSH_PAYLOAD.md`) —
  **한쪽만 고치면 어긋난다.**
- 받는 사람의 **프로필을 고른 기기**(`device.profile_id`)로만 나간다. 기기가 프로필을 바꾸면
  `/api/app/push/token` 으로 알려줘야 대상이 맞는다.
- 발송 이력을 남기지 않는다(알림과 다른 점). 메시지 자체가 DB 에 남아 있고 못 받은 푸시는
  앱을 열면 목록에 그대로 보인다 — 기기 × 메시지만큼 행을 쌓을 이유가 없다.

## 5. 앱이 해야 할 일

1. `data.type === 'chat'` 인 푸시를 **알림과 같은 경로로 처리**한다. 새 타입이지만 형식은 같으니
   기존 라우팅(`webBaseUrl + route`)이 그대로 동작해야 한다. 모르는 `type` 이 와도 죽지 않을 것.
2. 웹뷰가 `/?chat=<id>` 로 열리면 웹이 그 대화를 띄운다. 셸이 따로 할 일은 없다.
3. **프로필이 바뀌면 반드시 토큰을 다시 등록한다.** 채팅 푸시 대상은 전적으로
   `device.profile_id` 로 갈린다 — 이 값이 낡으면 남의 메시지 알림이 간다.
4. 배지 숫자(안 읽은 수)는 아직 푸시에 싣지 않는다. 필요하면 여기에 요청을 적어둘 것 —
   `data` 에 필드를 **추가**하는 방식으로만 확장한다(구버전 셸 호환, AGENTS.md §2).

### 진행 상황 (2026-08-13)

1~3 은 셸에 들어갔다(`nuplex-app/docs/plan/active/phase-7-chat-push.md`). 그러면서
셸에서 두 가지가 드러났다.

- **프로필을 바꿔도 토큰을 다시 등록하지 않고 있었다.** 셸이 FCM 토큰이 바뀔 때만
  재등록해서, 프로필을 바꿔도 서버에는 이전 `device.profile_id` 가 남았다. 지금은
  `notifyWebReady` 마다 토큰과 프로필 쿠키를 함께 보고 판단한다. **이 신호는 프로필
  선택이 전체 페이지 이동일 때만 온다** — `components/profile-picker.tsx` 의
  `window.location.assign` 을 클라이언트 라우팅으로 바꾸면 이 경로가 깨진다.
- **Android 는 백그라운드에서 시스템이 알림을 그린다.** 서버가 `notification` 과 `data`
  를 함께 보내기 때문이다. 그때 탭하면 `data` 가 인텐트 extras 로 들어오는데 셸이
  자기 키만 읽고 있어 라우트를 잃었다. 셸에서 고쳤다.

웹 쪽도 하나 고쳤다 — `proxy.ts` 가 `next` 를 경로로만 만들어서 `/?chat=12` 의 쿼리가
버려지고 있었다. 로그인·프로필 선택을 거쳐 들어와도 대화가 열리도록 쿼리를 함께 싣는다.
